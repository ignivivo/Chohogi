## 0. 왜 갈아엎나 (측정된 사실)

- 2026-09-22 이후 커밋 29개가 모두 초호기 자신을 고친 작업이었다. 제품 작업 성과의 증거는 없다.
- 효과가 측정된 것은 작은 핵심뿐이다: 주입 지침의 테스트 우선·완료 주장 관문(replay에서 초호기 있을 때만 준수).
- 작은 작업 replay 26개에서 route 문서 읽기는 4회, skill 호출 0회. 큰 대화형 작업에서는 읽었다(표본 차이 주의).
- 같은 실패 유형이 이틀 동안 2~5회씩 반복됐다(`execution-record.py learning-scan`).
- 커뮤니티·연구의 공통 결론: 정교한 프레임워크는 호불호가 크고, "기본 도구 + 고른 skill 몇 개 + 짧은 지침"이 많이 추천된다.
  하네스 설계 실증 연구(arXiv 2609.20804)는 "모델에 맞춘 최소주의"를 결론으로 낸다.
- 근거: `DBG-20260930-diagnosis-phase2`, `HOM-20261001-guidance-slim`, `HOM-20261001-loop-engine-and-pruning`.

## 1. 결정된 원칙 (사용자와 합의, 2026-10-01)

1. **기능이 먼저다.** 필요한 기능을 정하고, 그 기능을 호스트(Claude Code·Codex)나 외부 skill이 이미 제공하면 초호기는
   만들지 않는다. 식물 기관 분류는 버린다. 생물학은 기능 배치의 설계 언어로만 쓴다.
2. **공생체(세포내 공생 모델).** 외부 skill·하네스는 복사하지 않고 고정 버전 그대로 쓴다(자기 게놈 유지). 융합(복사해
   다시 쓰기)은 공생자가 오래 필수이고 원본 변화가 위험이 될 때만 한다.
3. **상시 통제자는 하나.** 초호기의 얇은 핵심만 push(세션 시작 주입)한다. 공생자는 pull(불릴 때만)로만 받는다.
   공생자의 session-start hook과 강제 실행은 끈다. pull로 쓸 수 없으면 필요한 skill만 떼어 쓰거나 거부한다.
4. **기능당 제공자 하나.** 공생자를 들이면 초호기의 같은 기능을 뺀다. 더하지 않고 바꿔 끼운다.
5. **무게 예산.** 초호기가 세션에 더하는 양을 첫 턴 기준 약 7k 토큰 이하로 묶는다(현재 측정치). 새 구성 요소는 같은 만큼
   빼야 들어온다. 주입 지침 4,000자 상한 유지.
6. **방지턱 금지.** 지시받은 작업은 막지 않는다. 모델 선택·감시·심사는 보고만 하고 작업을 멈추지 않는다. grill 계열처럼
   질문을 이어가는 skill은 사용자가 부르거나 큰 계획에서만 쓴다.
7. **증거로 남기고 뺀다(RRSI 원칙).** 구성 요소를 넣거나 바꾸면 replay로 비교한다. 노이즈 폭 안의 차이는 "변화 없음"이다.
   비용이 늘고 이득이 노이즈를 넘지 못하면 되돌린다. 특정 시나리오에만 맞춘 변경은 거른다.
8. **정책 결정은 사용자가 한다.** 비용·되돌리기 어려움·사용자 결과가 달라지는 선택은 추천까지만 한다.

## 3. 목표 구조

### 3.1 기능 지도 (착수 첫 단계에서 실측으로 채운다)

필수 기능마다 제공자를 하나만 정한다. 제공자는 호스트, 공생자, 초호기 중 하나다. "있다"는 실제 작동 확인으로만 인정한다.

| 기능 | 제공자 후보 | 초호기가 직접 가질지 |
|---|---|---|
| 계획·결정의 빈틈 잡기 | Matt Pocock `/grill-with-docs`, 호스트 계획 모드 | 아니요 |
| 테스트 우선, 완료 전 검증 | 초호기 핵심 지침(효과 확인됨) | 핵심 지침 몇 줄 |
| 체계적 디버깅 | Superpowers skill 또는 초호기의 짧은 규칙 | 한 벌만 |

### 3.2 초호기가 소유하는 것

1. **얇은 핵심 지침**(약 2,000자 이하): 테스트 우선과 핑계 금지, 완료 주장 관문, 큰 결정은 사용자에게, 방지턱 금지, 개인 선호.
2. **공생자 등록부 + 막 검사**: 공생자마다 출처, 고정 버전, 맡는 기능 하나, pull 전용 여부와 끈 hook, 허용 쓰기 경로,
   입장 증거, 측정된 비용과 기여, 상태. 출발점은 기존 `.agents/chohogi-external-capabilities.json` 계약과
   `verify-external-capability-contract.py`, 공급망 검사 `scan-skill-intake.py`.
3. **공생자 일생**: `후보 → 격리 시험 → 관용 → 제재 또는 퇴출`. 입장 신호 확인, 공급망 검사, 무임승차 제재(비용 대비 기여),
   업데이트 시 재심사, 깨끗한 퇴출(폴더·hook·설정 잔여물 없음).
4. **NK 감시(선천 면역)**: 모든 구성 요소(규칙, 역할, 공생자, 참조 문서)는 자기 표지(작동을 확인하는 검사)를 하나 이상
   선언한다. 표지가 없거나 실패하면 보고한다. 정정 제안은 세 갈래: 지켜지게 만들기, 연결 고치기, 제거. 보고만 하고 작업을 막지 않는다.
   비용 단계: 상시 정적 검사(0) → **실제 작업 세션 transcript 수동 관측(추가 모델 비용 0)** → 변경 시 replay → 주기 표본(L1).
5. **적응 면역(learning, 최소형)**: 사용자 교정을 기록하고, 같은 유형이 두 번 나오면 검사로 만든다. 이미 실패한 검사를
   다시 대는 것은 허용하지 않는다(현재 구현의 구멍).
6. **측정(항상성)**: `adherence-replay.py`에 노이즈 폭과 비용 대비 수용 규칙을 붙인다. 제품 프로젝트 실사용이 holdout이다.
7. **호스트 연결**: 역할 등록(`codex-role-setup.py`), 모델 카드(간소화).

## 4. 비용 통제

- 세션 무게: 첫 턴 약 7k 토큰 이하(1장 5번).
- 초호기 소유물: 문서 약 500줄, 도구 3~5개 이내.
- replay: 결정에 쓰는 비교는 시나리오당 2~3회. 비용은 `evaluation-budget-policy.md` 안에서 쓰고 기록한다.
- 심사·감시는 공생자를 들이거나 바꿀 때와 주기 점검에서만 돌린다. 일상 작업에서는 정적 검사와 수동 관측만.
