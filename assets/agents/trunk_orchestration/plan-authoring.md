# 계획 작성 계약

설계·요구가 확정된 뒤 여러 작업으로 나뉘는 구현을 위해 활성 계획(`document-lifecycle.md`의
`active-plan`)을 쓸 때 적용한다. 한 경계의 짧은 변경에는 계획 문서를 만들지 않는다.

## 독자와 목적

계획의 독자는 이 코드베이스와 설계를 본 적 없는 실행자다. 그는 인터페이스와 테스트가
정해지면 그 언어의 관용적인 코드를 쓸 수 있고, 계획이 열어 둔 곳에서는 합리적으로
고른다. 그가 알 수 없는 것은 **integrator가 이미 내린 결정** — 어떤 파일, 어떤 이름과
시그니처, 설계의 어떤 값, 어떤 테스트가 각 작업을 증명하는지 — 이다. 계획은 그 결정의
집합이다.

## 위치와 머리말

- 저장 위치는 프로젝트 문서 registry가 정한 계획 위치다. registry가 없으면
  `document-lifecycle.md`의 종료 검사대로 registry부터 선언한다. 도구 이름이 붙은
  고정 경로를 쓰지 않는다.
- 새 계획을 활성 계획으로 등록하면 이전 활성 계획은 `historical`로 바꾸고 내부 배너도
  함께 바꾼다. 활성 계획은 최대 하나다. 계획의 execution record가 finalize되면 그 계획도
  `historical`로 바꾸고, 다음 계획이 없으면 registry의 `activeExecutionPlan`을 `null`로 둔다.
  프로젝트가 실행 기록(`docs/work-log/records/`)을 쓰면 활성 계획 항목에 `executionRecord`를 반드시 적고,
  검증기가 그 기록의 종료 여부와 대조한다.
- 머리말: 목표 한 문장, 접근 2–3문장, 기술 스택, 근거 설계 문서 경로, 전역 제약,
  검토 초점. 실행 방법은 `execution-allocation.md`와 `task-loop.md`가 정한다고 한 줄로
  적는다. 특정 외부 스킬·도구를 실행하라는 지시를 계획 문서에 넣지 않는다 — 계획은
  나중에 다른 세션이 읽으며, 그 안의 호출 지시는 그 세션의 conductor를 우회한다.

## 범위와 파일 구조

1. 설계가 서로 독립된 하위 시스템 여러 개를 덮으면 하위 시스템마다 계획을 나눈다.
   각 계획은 혼자서 동작하고 검증 가능한 결과를 낸다.
2. 작업을 나누기 전에 만들거나 바꿀 파일과 각 파일의 책임을 먼저 정한다. 파일 하나에
   책임 하나, 함께 바뀌는 파일은 함께 둔다. 기존 코드베이스에서는 기존 패턴을 따르고,
   바꾸려는 파일이 이미 지나치게 크면 분할을 계획에 넣을 수 있다.

## 작업 크기

작업은 자기 테스트 주기를 갖고 독립 검토의 한 관문이 될 가치가 있는 가장 작은 단위다.
설정·골격·문서 단계는 그것을 필요로 하는 작업에 합친다. reviewer가 한 작업은 반려하고
이웃 작업은 승인할 수 있는 곳에서만 나눈다. 각 작업은 독립적으로 검증 가능한 산출물로
끝난다.

각 작업에는 다음을 둔다.

- **파일:** 만들 파일, 바꿀 파일(가능하면 줄 범위), 테스트 파일의 정확한 경로
- **인터페이스:** 소비 — 앞 작업에서 쓰는 것의 정확한 시그니처. 생산 — 뒤 작업이 쓰는
  이름·매개변수·반환 형태. 실행자는 자기 작업만 보므로 이웃 작업의 이름은 여기서만 안다.
- **단계:** 한 단계는 확인 가능한 결과가 있는 행동 하나다. 실패 테스트 작성 → 실행해 실패
  확인(예상 실패 메시지) → 구현 → 실행해 통과 확인 → 커밋.

## 단계에 담는 것

단계는 실행자가 합리적인 것 하나만 쓸 수 있을 때 완성된다 — 모호하지 않으면 되고,
전부 쓸 필요는 없다.

- 테스트 단계: 테스트 이름과 단언을 코드로, 설계의 정확한 값을 넣어서
- 코드 단계: 정확한 시그니처와 파일, 설계가 고정한 값. 본문은 시그니처와 테스트가
  정하지 못하는 알고리즘이나 설계가 고정한 문구일 때만
- 검증 단계: 실행할 명령과 통과를 뜻하는 출력
- 다른 작업 참조: 그 작업의 인터페이스 항목을 가리키고 코드를 반복하지 않는다

아무것도 정하지 않는 줄("추후", "예외 처리 추가", "위에 대한 테스트 작성", 어느 작업도
정의하지 않는 이름)은 빈칸이다. 코드보다 긴 계획은 계획이 아니라 코드를 대신 쓴 것이다.

## 전역 제약과 검토 초점

- **전역 제약:** 설계의 프로젝트 전역 요구(버전 하한, 의존성 제한, 명명·문구 규칙, 플랫폼
  요구)를 설계 원문의 정확한 값으로 한 줄씩. 모든 작업의 요구에 암묵적으로 포함된다.
- **검토 초점:** 설계가 암시하지만 어느 작업의 테스트도 다루지 않는 입력·실패 조건 중
  사용자를 가장 먼저 다치게 할 다섯 가지를, 합리적인 사람이 기대할 동작과 함께 적는다.
  설계가 침묵한 입력이라고 프로그램이 깨져도 된다는 뜻이 아니다. 각 줄에는 그것을
  고정하는 테스트를 담당 작업에 추가한다. 비어 있으면 확인했고 없었다는 뜻이다.

## 자기 점검

계획을 다 쓴 뒤 설계를 다시 펴고 스스로 확인한다(별도 위임 아님).

1. 설계의 각 요구에 대응하는 작업을 가리킬 수 있는가. 없으면 작업을 추가한다.
2. 모든 단계가 합리적인 것 하나만 쓰게 하는가. 빈칸과 코드 필사를 모두 고친다.
3. 뒤 작업이 쓰는 이름·시그니처가 앞 작업의 정의와 같은가.
4. 검토 초점의 각 항목에 테스트가 있는가.
5. 계획이 설계보다 몇 배 길면 본문을 시그니처·테스트 이름·단언으로 줄인다.

찾은 문제는 그 자리에서 고친다.

## 인계

계획을 저장하고 자기 점검을 마치면 사용자에게 경로를 알리고 계획이 원하는 것을 담았는지
검토를 요청한다. 실행 형태는 사용자 메뉴가 아니다 — `execution-allocation.md`가 정하고,
실행은 `task-loop.md`를 따른다. 사용자가 이미 실행 방식을 지정했다면 그것을 따른다.
