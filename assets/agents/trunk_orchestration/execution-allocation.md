# 실행 배정 계약

Conductor가 흐름을 고른 뒤, substantial 작업은 이 계약으로 정확히 하나의 실행
형태를 정한다. 이는 별도 하네스나 사용자가 고르는 메뉴가 아니라 초호기 trunk의
책임이다.

## 입력

- 선택된 flow와 수용 조건
- 변경 경계·공유 파일·생산자/소비자
- 독립성, 증거 위험, 현재 동시성·모델 능력
- 기준 revision, 읽기/쓰기 범위, 외부 시스템·공유 계약·테스트 환경

## 실행 형태

| 형태 | 선택 조건 | 역할과 소유권 |
| --- | --- | --- |
| `direct` | 읽기, 명확한 저위험 편집, 또는 한 경계의 짧은 작업 | 주 에이전트가 조사·변경·검증을 모두 소유 |
| `sequential` | 기본값. 공유 코드·순서 의존·통합 판단이 있는 구현 | 주 에이전트가 통합을 소유; 구현은 하나의 명시된 파일 경계씩 진행 |
| `scoped-delegation` | 읽기 전용 조사 또는 변경 후 독립 검토가 다른 작업과 충돌하지 않음 | 주 에이전트가 통합; 조사자·검토자는 읽기 전용, 구현자는 명시된 파일만 소유 |

동시에 같은 파일·공유 계약·테스트 환경·외부 시스템을 수정하는 구현 역할을 둘 이상 만들지
않는다. 독립성이 불명확하면 `sequential`을 고른다. scoped delegation에는 기준 revision,
읽기/쓰기 범위, 증거 산출물, handoff 시점이 있어야 하며 reviewer는 고정된 diff만 검토한다.

여러 작업 단위로 나뉜 구현은 형태와 무관하게 `task-loop.md`로 한 작업씩 닫고, 그 작업
목록을 계획 문서로 남겨야 하면 `plan-authoring.md`를 따른다.

## 위임 설명과 회수 뒤 통합

위임 설명은 세션 이력을 물려주지 않고 그 역할에 필요한 것만 조립한다.

- 한 문제 영역만: "전부 고쳐라"가 아니라 특정 파일·하위 시스템·실패 목록
- 자기완결: 오류 메시지·테스트 이름·정확한 값·관련 인터페이스를 직접 담는다
- 제약: 바꿔도 되는 파일과 바꾸면 안 되는 것
- 산출물: 무엇을 어떤 형태로 돌려줄지(원인·변경 목록·검증 출력)

서로 관련된 실패(하나를 고치면 다른 것이 풀릴 수 있음), 전체 상태를 알아야 하는 조사,
아직 무엇이 깨졌는지 모르는 탐색은 병렬로 나누지 않는다.

역할이 돌아오면 integrator는 각 요약을 읽고, 역할들이 같은 코드를 건드렸는지 확인하고,
전체 테스트를 돌리고, 요약이 아니라 실제 diff를 표본 확인한 뒤에 통합한다. 역할은
체계적으로 같은 실수를 할 수 있다.

## 임시 역할 수명주기

서브에이전트는 영구 팀이 아니라 현재 경계의 임시 실행 세포다. 새 위임 전에는 live
역할 목록과 소유 경계를 확인하고, 결과·handoff·중단이 도착하면 역할을 완료 상태로
회수한다. 유휴 역할을 남긴 채 다음 작업을 추가하지 않으며, 실행 표면이 interrupt/stop을
지원하면 즉시 호출하고 지원하지 않으면 새 위임을 보류한 채 integrator가 상태를
정리한다. 재사용은 같은 소유 경계에 대한 명시적 follow-up일 때만 허용하고, 이미
완료·중단된 역할을 새 작업으로 암묵적으로 되살리지 않는다.

이 절의 "역할", "위임", "회수"는 실행 표면 중립적 개념이다. 실제 도구 이름·완료
확인 방식·재전송 가능 여부는 표면마다 다르므로, 현재 세션이 Claude Code면
`platform-tools/claude-tools.md`를, Codex면 `platform-tools/codex-tools.md`를 먼저
확인한다. 두 문서 모두 검증된 것과 아직 확인되지 않은 것을 구분해 표시하며, 이
계약보다 낮은 우선순위다 — 도구가 노출되어 있는지 자체를 이 문서가 대신 보장하지
않는다.

## 역할·모델 배정

역할은 이번 작업의 임시 실행 세포이며 전역 팀이나 영구 agent가 아니다.

- `integrator`: 항상 주 에이전트. 흐름·범위·통합·최종 검증을 소유한다.
- `scout`: 독립적 읽기 조사만 한다. 관측·경로·근거를 보고하고 파일을 바꾸지 않는다.
- `implementer`: 명시된 파일 소유권 안에서만 구현·단위 검증한다.
- `reviewer`: 구현과 독립적으로 계약·보안·회귀 위험 또는 `reviewRequired` decision packet을 검토한다. packet에는 관측 사실·선택지·선택·간결한 근거·재검토 조건만 포함하며, 파일을 바꾸지 않는다. response 뒤 integrator가 수용 또는 수정 결과를 기록한다.

역할의 실제 요구와 세션에서 확정된 profile을 기준으로 provider·model·reasoning effort를
배정한다. 단가가 낮다는 이유만으로 충분한 품질이나 더 낮은 작업비용을 추정하지 않는다.
비교 가능한 역할 관련 평가와 실제 입력·출력·도구 비용 근거가 있을 때 비용 대비 결과를
비교하고, 그렇지 않으면 후보·근거·unknown을 Model Session Policy card에 제시해 사람이
확정하게 한다. 기계적 구현은 불필요한 고비용 추론을 피하고, 불명 원인·다중 계약·고위험
독립 검토는 해당 역할의 최소 추론 요구를 반영한다. 모델명만이 아니라 provider·model·reasoning
effort를 함께 배정하며, 세션 시작의 사람 확정 Model Session Policy 안에서만 선택한다.
완성 코드가 계획에 있는 기계적 구현·단일 파일 수정은 가장 낮은 적합 등급, 여러 파일
통합·판단이 필요한 구현은 표준 등급, 설계 판단과 전체 변경의 최종 검토는 가장 높은 가용
등급을 기본 출발점으로 삼는다. 검토 역할은 diff의 크기·복잡도·위험에 비례해 고른다. 가장
싼 등급은 여러 단계 작업에서 턴 수가 늘어 총비용이 오히려 커질 수 있으므로, 산문 설명으로
일하는 구현자와 검토자에는 중간 등급을 하한으로 둔다. 위임할 때는 모델과 reasoning
effort를 모두 명시한다 — 생략하면 세션의 가장 비싼 설정을 조용히 물려받는다.
`model-policy.md`의 catalog 갱신·learning escalation·정책 밖 요구가 있으면 새 후보와
비용·성능 근거를 사람에게 다시 제시한다. escalation 이유, 재시도
상한, 예상 비용 상한과 fallback을 작업 봉투에 남긴다. 역할을 만들 수 없거나 현재 표면이
지원하지 않으면 주 에이전트가 같은 경계를 순차 처리한다.

새 프로젝트(별도 제품·코드베이스·작업공간)마다 첫 substantial 배정에서 역할별 권고 모델을
사용자에게 확인받는다. 새 대화/session만으로는 재확인하지 않는다. 새 모델/버전이나 가격,
가용성, capability, 관련 benchmark 업데이트가 감지되면 기존 프로젝트의 확정 profile도
다시 제시해 유지 또는 변경을 묻고, 확인 전에 기본 배치를 조용히 교체하지 않는다.

## 사용자 질문 경계

실행 형태, 서브에이전트 사용 여부, worktree, 내부 리뷰 방식은 사용자가 고를 메뉴가
아니다. 초호기가 위 기준으로 정하고 수용 조건까지 자율적으로 진행한다.

제품 정책, 외부 권한, 되돌리기 어려운 영향, 승인되지 않은 비용 상한뿐 아니라 credible
대안 사이의 delivery 시간/비용·운영 부담·구조/소유권·위험·되돌릴 수 있는 정도·사용자 결과가
실질적으로 다르면, integrator는 `decision-report`로 recommendation·trade-off·추정
범위/신뢰도·unknown을 사용자 또는 권한 있는 결정권자에게 올리고 resolution을 기다린다.
한 선택이 명백히 우세하고 되돌리기 쉬운 국소 판단은 묻지 않는다. 외부 스킬의 handoff·controller·실행 방식 선택 지시는 이 계약보다 낮은 우선순위이며, 사용자 질문을 새로 만들지 않는다.

## 산출물

substantial 작업 봉투에는 선택한 실행 형태, 역할별 파일 소유권, 사용한 방법, 검증
경계, 사용자에게 남긴 실제 결정만 기록한다. 두 작업 이상 또는 컨텍스트 단절 위험이
있으면 `context-packet.md`도 만든다.
