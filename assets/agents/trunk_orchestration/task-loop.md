# 작업 루프 계약

`execution-allocation.md`가 `sequential` 또는 `scoped-delegation`을 고른 뒤, 여러 작업
단위로 나뉜 구현(활성 계획의 작업 목록, 또는 integrator가 나눈 작업 경계)을 끝까지
실행하는 방법이다. 실행 형태와 역할은 allocation이 정하고, 이 계약은 그 안에서 한
작업씩 닫는 규칙만 정한다. 단일 경계의 짧은 `direct` 작업에는 적용하지 않는다.

## 기록 위치

진행 상태는 프로젝트의 `docs/work-log/records/<work-id>/`(execution record)에만 남긴다.
숨김 작업 폴더·홈 디렉토리·도구 이름이 붙은 별도 경로를 만들지 않는다. 대화 기억은
압축으로 사라지므로, 재개 시에는 기억보다 `handoff --work-id <id>`의 projection과
`git log`를 먼저 믿는다. 이미 `checkpoint`로 닫힌 작업은 다시 실행하지 않는다.

| 사건 | execution record 이벤트 |
| --- | --- |
| 작업 하나가 완료 계약을 충족 | `checkpoint --id task-<N>` (범위 커밋, 실행한 검증 명령과 결과) |
| 계획과 실제가 어긋나 integrator가 판정 | `decision` (관측·선택지·선택·틀렸을 때의 비용을 재검토 조건에) |
| 검토 지적을 미루거나 수용하지 않음 | `decision` — 조용히 버리지 않는다 |
| 계획 전체 종료 | `outcome` (판정 목록·미룬 지적·남은 위험) |

## 시작 전 점검

1. 활성 계획과 그 근거 문서(설계·요구)를 한 번 읽는다. 근거 문서가 없으면 이후 판정은
   잠정적이라는 사실을 `fact`로 남긴다. 계획과 근거 문서가 충돌하면 근거 문서가 우선한다.
2. 작업 사이 인터페이스 충돌을 먼저 본다. 한 작업이 만든 것을 다른 작업이 쓰는 쌍마다
   "생산 대 소비"를 대조하고, 각 작업이 자기 안에서 일관된지(명시한 테스트와 코드, 만드는
   파일과 나중에 고치는 파일) 확인한다. 발견한 충돌은 실행 전에 판정해 `decision`으로
   남긴다. 공유하는 것이 없으면 그 사실을 한 줄로 남긴다.
3. 격리 작업공간이 필요한지 `platform-tools/`의 격리 절차로 판단한다.

## 작업 하나를 닫는 순서

1. **작업 설명을 파일로 준다.** 위임할 때는 그 작업의 요구·정확한 값·인터페이스만
   담은 작업 설명과 결과 보고 경로를 넘긴다. 이전 작업들의 요약이나 세션 이력을
   붙이지 않는다. 계획 전체를 읽게 하지 않는다. 직접 실행할 때도 기억한 요약이 아니라
   작업 설명의 원문을 다시 읽는다.
2. **실패 조건부터.** 테스트가 의미 있는 보호막이면 `delivery.md`의 테스트 우선 규칙대로
   실패를 먼저 확인한다.
3. **예상과 실제를 대조한다.** 명령을 실행하는 단계마다 예상 결과와 실제 출력을 비교한다.
   - 일치: 다음 단계.
   - 코드가 틀림: `debugging` route의 원인 규명 순서를 따른다. 출력만 맞추는 증상 수정은
     하지 않는다.
   - 계획이 틀림(근거 문서와 모순, 앞 작업 인터페이스와 불일치, 실행 불가능한 명령):
     근거 문서를 만족하는 가장 작은 변경으로 판정하고 `decision`으로 남긴 뒤 계속한다.
     기록 없는 이탈은 사용자 모르게 내린 결정이다.
4. **완료 계약.** 다음이 이 세션의 실제 실행 증거로 모두 참일 때만 `checkpoint`로 닫는다:
   작업 설명이 요구한 테스트가 존재하고 실행됐고 출력을 읽었다, 마지막 실행이 통과했다,
   모든 예상 결과를 실제 출력과 대조했다, 모든 이탈에 `decision`이 있다.
5. **위임 결과는 보고가 아니라 diff로 확인한다.** implementer의 "완료" 보고는 증거가
   아니다. 변경 범위 diff와 검증 출력을 직접 확인한다.

같은 모양의 작은 변경(여러 파일의 같은 한 줄 수정 등)은 작업마다 위임하지 않고 한 번의
위임으로 묶어 하나의 단위로 검토한다. 같은 파일·공유 계약을 동시에 고치는 implementer는
둘 이상 만들지 않는다.

## 위임한 작업의 검토와 수정 반복

`scoped-delegation`으로 구현을 위임했으면, 각 작업은 독립 reviewer의 두 판정 —
요구 충족과 작업 품질 — 을 모두 받아야 닫힌다. implementer의 자기 검토는 이를 대체하지
않는다. implementer는 스스로 reviewer나 다른 역할을 만들지 않는다.

- reviewer에게는 작업 설명·결과 보고·기준 revision부터 현재까지의 고정 diff 파일과,
  그 작업을 묶는 전역 제약 원문만 넘긴다. 특정 지적을 "하지 말라"거나 등급을 미리
  정해 주지 않는다 — 그것은 검토를 앞질러 판정하는 것이다.
- reviewer가 diff만으로 확인할 수 없다고 표시한 항목은 integrator가 교차 작업 문맥으로
  직접 확인한다. 실제 결함이면 요구 미충족과 같이 다룬다.
- 경미한 지적은 수정 반복에 넣지 않고 `decision`으로 미뤄 두며, 최종 검토가 다시 본다.
- 수정 반복은 한 번의 수정과 한 번의 범위 한정 재검토가 한 라운드다. 최대 5라운드:
  1–3라운드는 같은 implementer에게 열린 지적을 그대로 보낸다(재개 가능 여부는
  `platform-tools/`를 따른다). 4–5라운드는 한 단계 높은 모델의 새 implementer에게 작업
  설명·보고 파일·열린 지적을 넘긴다. 매 라운드 수정 보고에 해당 테스트·명령·출력이
  있어야 재검토를 보낸다. integrator는 직접 고치지 않는다 — 검토를 건너뛰게 된다.
- 5라운드 뒤에도 열린 지적은 integrator가 판정한다: reviewer가 틀렸거나 다툼이 있음 /
  실제지만 이후 작업이 의존하지 않음 / 실제이고 이후 작업이 의존함. 마지막 경우는
  이후 작업을 풀어 줄 가장 작은 변경으로 판정해 다음 작업 설명에 싣는다. 모든 판정은
  `decision`이다. 상한 전에 판정으로 반복을 끝내지 않는다.

implementer 보고 상태별 처리: 완료 → 검토로. 우려와 함께 완료 → 정확성·범위 우려면
검토 전에 해소. 문맥 부족 → 빠진 문맥을 주고 다시 위임. 막힘 → 문맥 문제면 같은
모델로 보강, 추론 부족이면 상위 모델, 너무 크면 분할, 계획이 틀렸으면 판정 후 재위임.
막혔다는 보고에 아무것도 바꾸지 않고 같은 조건으로 재시도하지 않는다.

## 최종 검토

모든 작업이 닫히면 분기 시작점부터 현재까지의 전체 변경을 독립 reviewer 한 명이 본다.
작업별 검토를 하지 않은 직접 실행(`sequential`)에서는 이것이 유일한 새 시각이므로
생략하지 않는다. reviewer가 없는 실행 표면이면 integrator가 별도 통과로 같은 기준을
적용하되, 작성자 자기 검토라는 한계를 결과에 명시한다.

- reviewer의 등급은 참고다. 근거 문서가 침묵한 입력이라는 이유로 낮게 매긴 지적은,
  그 소프트웨어를 쓰는 합리적인 사람이 겪을 영향으로 다시 등급을 매긴다.
- 치명·중요 지적은 한 번의 수정 통과로 모두 고친다. 각 수정은 그 지적을 재현하는
  테스트가 먼저 실패하고 통과하는 것으로 확인하고 전체 테스트를 다시 돌린다. 두 번째
  수정 통과는 없다.
- 고치지 않기로 한 지적과 경미한 지적은 `decision`으로 남긴다.

## 계속 진행과 멈춤

사용자가 계획 실행을 맡겼으면 작업 사이마다 "계속할까요"를 묻지 않는다. 충돌·모호함·
계획 결함은 판정하고 기록한 뒤 진행한다. 멈추고 묻는 것은 `authority-lattice.md`에서
별도 근거가 필요한 것 — `external-side-effect`(병합·공유 브랜치 push·배포·메시지),
`irreversible-or-costly-action`, 보안 경계(`../security_immune_system/boundary-policy.md`)
— 과, 모든 진행 경로가 추측뿐인 계획 결함(`decision-report`)뿐이다.

## 종료 보고

최종 보고에는 이 루프에서 내린 모든 판정을 순서대로, 각각 틀렸을 때의 비용과 함께
빠짐없이 나열하고, 미룬 경미 지적도 따로 나열한다. 사용자를 대신해 내린 결정이 사용자에게
닿는 곳은 이 목록뿐이다. 이후 통합(병합·PR·보존)은 `delivery.md`의 통합 종료를 따른다.
