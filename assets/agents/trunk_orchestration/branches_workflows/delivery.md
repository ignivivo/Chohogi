# Delivery route

<!-- chohogi:section=role -->
## 역할

확정된 요구사항을 가장 작은 안전한 변경으로 구현하고, 요구된 성공 조건을 검증
증거와 함께 제공한다. 이 route는 제품 결정을 다시 열거나 검증 없는 완료를 선언하지
않는다.

<!-- chohogi:section=entry -->
## 진입 조건

- 사용자 목표, 범위, 수용 조건이 충분히 확정되어 있다.
- 코드·문서·구성·테스트 등 지속 변경을 구현해야 한다.
- 변경의 생산성·위험·조건이 단순 직접 처리 범위를 넘는다.

<!-- chohogi:section=negative-scope -->
## 사용하지 않는 경우

- 중요한 제품 선택이 열려 있으면 `product-decision`을 선택한다.
- 관측 가능한 실패는 있으나 원인을 모르면 `debugging`을 선택한다.
- 단순 질문, 읽기 전용 확인, 명확한 저위험 한 줄 편집은 직접 처리한다.

<!-- chohogi:section=input -->
## 입력

- 확정된 요구사항과 제외 범위
- 수용 조건·관련 계약·영향받는 소비자
- 현재 작업 트리 상태와 기존 테스트·배포 제약

<!-- chohogi:section=method -->
## 절차

1. 코드 전에 프로젝트 진입점을 확인한다. 저장소 root와 가장 가까운 `.agents`, 호환 `.agent`,
   `AGENTS.md`, 로컬 skill, 기존 변경을 확인하고, 적용할 project leaf 또는 `없음`이라는
   결과를 작업 봉투에 남긴다. leaf가 없다는 사실만으로 자동 생성하지 않으며, 반복되는
   프로젝트 경계·소유자·실제 검증이 확인될 때만 Learning의 귀속 절차로 만든다.
2. 요청의 동사를 구현 방식으로 성급히 번역하지 않는다. `숨김`, `코멘트 아웃`, `제거`,
   `정리`처럼 범위를 바꿀 수 있는 표현은 사용자 가시 결과, 적용할 경로·소비자, 유지할
   소비자, 되돌릴 표현을 먼저 의도 계약으로 정한다. 이전 대화·스크린샷·명시된 제외 범위로
   해소되지 않는 모호성만 코드 수정 전에 질문한다.
3. 코드 전에 필요한 범위를 정찰한다. 처음 보는 프로젝트, 기존 변경이 있는 작업 트리,
   공통 구성요소·설정·스타일·데이터 계약 또는 여러 경로 소비자를 바꾸는 작업에서는
   `작업 트리와 기존 diff`, `실행 명령·프레임워크·진입 경로`, `요청 경로에서 변경
   컴포넌트까지의 구성`, `정의·import·호출·조건부 렌더링·데이터 소비의 참조 그래프`,
   `상위 layout·전역 규칙·페이지 규칙·컴포넌트 규칙의 우선순위`를 먼저 확인한다.
   이는 모든 파일을 기계적으로 읽으라는 뜻이 아니라, 수정할 뿌리와 실제 소비 경계를
   발견할 만큼의 지도다. 코드 수정 전에는 이 지도, 요청됨·필수·선택의 범위 분류,
   제외 범위, 수용 조건별 검증 계획을 남긴다. 증거 없이 공통 규칙을 바꾸거나
   하위 요소만 반복 조정하지 않는다.
4. 요구사항·소비자·계약·작업 트리의 관련 범위를 확인한다. 컴포넌트·함수·자산·문구를
   숨기거나 바꾸는 경우에는 정의만 보지 말고 모든 import·호출·경로 노출 지점을
   검색한다. 요청한 소비자에서만 적용하고, 요청 밖 소비자가 유지되는지 함께 확인한다.
   `코멘트 아웃`은 지정된 모든 소비 지점에서 import와 렌더링 코드를 되살릴 수 있게
   보존하는 것을 뜻하며, 삭제·대체·고아 코드 억제 주석으로 바꾸지 않는다.
5. 위험과 독립성에 비례하는 최소 구현 계획을 세운다. 이미 승인된 계획을 다시
   장황하게 만들지 않는다.
6. 기능·버그 수정에서 테스트가 의미 있는 보호막이면 실패 조건을 먼저 명확히 하고
   구현한다. 기계적 문서 변경처럼 해당하지 않는 경우에는 억지 TDD를 적용하지 않는다.
7. 코드 전에 `../../security_immune_system/boundary-policy.md`의 risk signal을 분류한다. 신호가 있으면
   `pre-code-security-acceptance`를 수용 조건으로 먼저 남기고 해당 reusable method를 적용한다.
   scanner·release gate를 주장하면 프로젝트가 `project-execution-gate-required`의 실제 command,
   결과, fixture, nonzero failure path를 제공할 때만 그렇게 주장한다.
8. JSON·YAML·skill frontmatter·registry·fixture처럼 선언을 바꾸면 `python3 tooling/verify-semantic-assurance.py`로
   실제 엄격 해석을 먼저 확인한다. 초호기 기관·reusable method·tooling·설치/검증 adapter를 새로 만들거나 바꾸면,
   `../functional_assurance/registry.json`에서 기능 claim·실행 경로·resource·verifier·fixture·산출물·한계를 갱신하고
   `python3 tooling/verify-functional-assurance.py`를 실행한다. 이 검증 없이 해당 자산이
   실제 기능을 제공하거나 release를 막는다고 주장하지 않는다.
9. 필요한 기술·도메인 reusable method와 도구만 선택한다. 방법 선택은 `../method-selection.md`를
   따르되, 프로젝트 leaf는 해당 프로젝트에 실제 코드·CI·fixture가 필요한 반복 적응일 때만 만든다. route는 수용 조건·회귀 위험·검증 증거만 강제한다. 병렬 위임은 경계가
   독립적일 때만 한다.
10. 사용자 제공 스크린샷 또는 명시적 데스크톱·모바일 동작이 있으면, 코드 전에 각
   사용자 가시 변경을 `경로·컴포넌트·데스크톱 상태·모바일 상태·확인 방법`으로 묶은
   간결한 수용 매핑을 만든다. 주석 처리된 영역과 실제 렌더링 상태를 구분하고, 같은
   사용자 문구가 여러 컴포넌트에 있는지 확인한다. 매핑의 각 항목은 실제 경로와
   해당 viewport에서 확인한다. 브라우저나 데이터 조건을 충족하지 못하면 확인하지 못한
   항목으로 보고하며, 모바일에서 단순히 숨겨진 요소를 수용으로 간주하지 않는다.
   반응형 레이아웃은 단일 요소의 폭만 조정하지 말고, 섹션 순서와 인접한 반복 요소의
   열 수·폭·간격·정렬을 같은 breakpoint에서 함께 수용한다.
   PC·태블릿 분류는 기존 고정 데스크톱 폭을 보존하려고 비표준 대형 breakpoint로
   미루지 않는다. 프로젝트의 명시 기준이 없으면 모바일 `0~767px`, 태블릿
   `768~1023px`, PC `1024px~`를 검토 시작점으로 삼고, 각 전환점에서 실제
   컨테이너 폭·열 구성·가로 넘침을 함께 확인한다. 다른 기준을 채택하면 그 이유와
   검증 viewport를 수용 매핑에 남긴다.
   배너·썸네일처럼 고정 비율의 반복 시각 자산은 한 열일 때 남는 컨테이너 폭만큼
   무한히 확대하지 않는다. 자산의 최대폭과 정렬을 먼저 정하고, 여백이 과도해져
   복수 자산이 그 최대폭을 유지한 채 들어갈 수 있을 때 열 수를 늘린다.
   viewport breakpoint는 페이지의 구조 전환에만 쓰고, 재사용 컴포넌트의 열 수는
   실제 컨테이너 폭 또는 intrinsic grid로 결정한다. 중간 폭에서 고정 래퍼 폭이
   급격히 바뀌어 컴포넌트 열 수가 우연히 점프하지 않는지 확인한다.
   반응형 전환 수치를 보고할 때는 `컨테이너 임계값 공식`, `검증한 경로와 실제
   컨테이너 폭`, `viewport 환산에 포함되는 여백·스크롤바·safe area`를 분리해
   기록한다. 임계값의 바로 전·정확한 값·바로 다음 값을 같은 브라우저 환경에서
   확인하고, 환경별 viewport 관측값을 CSS 임계값이나 다른 환경의 보편 수치로
   바꾸어 말하지 않는다.
11. 변경 후 참조 그래프의 직접 소비자와 인접 계약을 검증한다. 사용자 가시 요구는 실제 브라우저와
   해당 viewport에서 확인한다. 자동화 daemon이 sandbox 경계에서 실패하면
   허가된 실행 경계로 한 번 재시도해 실제 측정·스크린샷을 얻고, 그래도 불가능할 때만
   미검증으로 보고한다. 계산된 CSS 값만으로 실제 화면 검증을 대체하지 않는다.
   테스트·린트·타입 검사·빌드·실행 중
   실패한 항목은 출력이 불충분해도 완료로 선언하지 않는다. 가능한 가장 작은 재현·상세 로그·실패
   계층을 확인해 원인 상태와 다음 진단을 남긴다. 사용자 또는 다른 프로세스가 실행 중인
   개발 서버와 같은 출력 디렉터리(예: Next의 `.next`)를 쓰는 production build·clean은
   병행하지 않는다. 격리된 worktree·출력 경계가 없으면 사용자에게 서버 중지·재시작을
   맡기고, 활성 dev 서버의 정상성을 build 성공으로 대체하지 않는다. 범위 밖 설정을 임의로 바꾸지 않으며, 차단이
   해소되지 않으면 미검증 항목으로 종료한다.
12. 실제 실행한 검증, 결과, 남은 위험을 사실대로 보고한다. 임시 테스트·스크린샷·서버·패치
    산출물은 최종 변경에 남길지와 보관 이유를 확인하고, 전달용 patch는 최종 diff에서 다시 만들고
    깨끗한 기준에 적용 가능한지 검증한다.

<!-- chohogi:section=optional-capabilities -->
## 선택적 능력

- 변경이 여러 독립 파일 경계로 나뉠 때만 병렬 조사·구현을 사용한다.
- 고위험 계약·보안·결제·개인정보 변경에서만 독립 검토를 요청한다.
- React 비동기 상태, 접근성, 성능, 보안 등 구체적 기술 경계가 맞을 때만 해당 reusable method를
  사용한다.

<!-- chohogi:section=exit -->
## 산출물과 종료 조건

산출물은 변경한 것, 수용 조건별 검증 증거, 실행하지 못한 검증, 남은 위험이다.
요구된 변경과 비례한 검증이 끝났거나, 외부 권한·사용자 결정 없이는 더 진행할 수
없는 지점이 명확해졌을 때 종료한다.

## 다음 분기

- 구현 중 중요한 요구사항 선택이 다시 열리면 `product-decision`으로 전환한다.
- 예상과 다른 실패의 원인이 불명확하면 `debugging`으로 전환한다.
- 확인된 실패가 재현 가능하고 예방 자산 가치가 있으면, 종료 뒤 phloem handoff를 통해
  `learning`으로 넘긴다. learning은 이 route와 병렬 활성화하지 않는다.
