# Delivery route

<!-- chohogi:section=role -->
## 역할

확정된 요구사항을 가장 작은 안전한 변경으로 구현하고, 요구된 성공 조건을 검증
증거와 함께 제공한다. 이 route는 제품 결정을 다시 열거나 검증 없는 완료를 선언하지
않는다.

<!-- chohogi:section=entry -->
## 진입 조건

- 사용자 목표, 범위, 수용 조건이 충분히 확정되어 있다.
- 코드·문서·구성·테스트 등 지속 변경을 구현해야 한다.
- 변경의 생산성·위험·조건이 단순 직접 처리 범위를 넘는다.

<!-- chohogi:section=negative-scope -->
## 사용하지 않는 경우

- 중요한 제품 선택이 열려 있으면 `product-decision`을 선택한다.
- 관측 가능한 실패는 있으나 원인을 모르면 `debugging`을 선택한다.
- 단순 질문, 읽기 전용 확인, 명확한 저위험 한 줄 편집은 직접 처리한다.

<!-- chohogi:section=input -->
## 입력

- 확정된 요구사항과 제외 범위
- 수용 조건·관련 계약·영향받는 소비자
- 현재 작업 트리 상태와 기존 테스트·배포 제약

<!-- chohogi:section=method -->
## 절차

Material 계획·문서를 유지하는 프로젝트는 `.agents/chohogi-document-registry.json`을
확인하고 `tooling/verify-project-document-registry.py --root <project>`를 먼저 실행한다.
registry가 없으면 문서 권위와 활성 계획을 선언할 수 있을 때까지 `defer`하거나 registry를
만드는 범위만 수행한다.
사용자가 여러 합의 항목을 함께 적용하라고 요청한 material 작업은 execution contract에
`requestedItems`를 만들고 각 항목을 `scope-item`으로 구현·보류·제외 처리하기 전에는
finalize하지 않는다.

1. 나중의 피드백·handoff·중단 재개·명시적 증명이 필요한 delivery는 먼저 execution record의 `begin`으로 기준본과 계약을 남긴다. 코드 전에 프로젝트 진입점을 확인하고, 경로·소비자·프레임워크·공통 컴포넌트/도메인 서비스·데이터/상태·기존 검증·관련 과거 피드백에서 재사용 가능한 능력을 찾아 capability map으로 기록한다. 프로젝트가 계획 문서를 유지하면 현재 큐와 완료 조건을 소유하는 활성 문서를 하나만 식별하고, 나머지 계획·감사·실행 기록은 역사 또는 증거로 분류한다. 소비자가 있는 수용 조건은 contract에 소비자별 `verified` artifact 또는 사유가 있는 `deferred` 상태를 선언한다. 다음 선택은 파일 확장자나 첫 구현 수단으로 축소하지 않고, 사용자 결과에서 프로젝트 구조·프레임워크/도메인 수단·컴포넌트/상태·국소 편집 순으로 내려오며 대안을 비교한다. credible 대안이 시간/비용·운영 부담·구조/소유권·위험·되돌릴 수 있는 정도·사용자 결과를 실질적으로 다르게 하면, agent는 recommendation과 trade-off·비용 범위/신뢰도·unknown을 `decision-report`로 보고하고 사용자 또는 권한 있는 결정권자의 `decision-resolution`을 기다린다. 이어 관측 사실·중요한 선택지·선택 이유·재검토 조건·결과를 기록한다. 되돌리기 어려운 판단, 공유·공개·보안 경계, 다투어진 근거, 반복 피드백 실패, 사용자가 요청한 독립 검토만 `reviewRequired`로 표시하고 map과 considered capabilities를 담은 packet에 대해 read-only reviewer의 response와 integrator의 수용·수정 결과를 남긴다. 단순 작업에 고정 node나 기록을 강제하지 않는다. 저장소 root와 가장 가까운 `.agents`, 호환 `.agent`,
   `AGENTS.md`, 로컬 skill, 기존 변경을 확인하고, 적용할 project leaf 또는 `없음`이라는
   결과를 작업 봉투에 남긴다. leaf가 없다는 사실만으로 자동 생성하지 않으며, 반복되는
   프로젝트 경계·소유자·실제 검증이 확인될 때만 Learning의 귀속 절차로 만든다.
2. 요청의 동사를 구현 방식으로 성급히 번역하지 않는다. `숨김`, `코멘트 아웃`, `제거`,
   `정리`처럼 범위를 바꿀 수 있는 표현은 사용자 가시 결과, 적용할 경로·소비자, 유지할
   소비자, 되돌릴 표현을 먼저 의도 계약으로 정한다. 이전 대화·스크린샷·명시된 제외 범위로
   해소되지 않는 모호성만 코드 수정 전에 질문한다.
3. 코드 전에 필요한 범위를 정찰한다. 처음 보는 프로젝트, 기존 변경이 있는 작업 트리,
   공통 구성요소·설정·스타일·데이터 계약 또는 여러 경로 소비자를 바꾸는 작업에서는
   `작업 트리와 기존 diff`, `실행 명령·프레임워크·진입 경로`, `요청 경로에서 변경
   컴포넌트까지의 구성`, `정의·import·호출·조건부 렌더링·데이터 소비의 참조 그래프`,
   `상위 layout·전역 규칙·페이지 규칙·컴포넌트 규칙의 우선순위`를 먼저 확인한다.
   이는 모든 파일을 기계적으로 읽으라는 뜻이 아니라, 수정할 뿌리와 실제 소비 경계를
   발견할 만큼의 지도다. 코드 수정 전에는 이 지도, 요청됨·필수·선택의 범위 분류,
   제외 범위, 수용 조건별 검증 계획을 남긴다. 증거 없이 공통 규칙을 바꾸거나
   하위 요소만 반복 조정하지 않는다.
4. 요구사항·소비자·계약·작업 트리의 관련 범위를 확인한다. 컴포넌트·함수·자산·문구를
   숨기거나 바꾸는 경우에는 정의만 보지 말고 모든 import·호출·경로 노출 지점을
   검색한다. 요청한 소비자에서만 적용하고, 요청 밖 소비자가 유지되는지 함께 확인한다.
   `코멘트 아웃`은 지정된 모든 소비 지점에서 import와 렌더링 코드를 되살릴 수 있게
   보존하는 것을 뜻하며, 삭제·대체·고아 코드 억제 주석으로 바꾸지 않는다.
5. 위험과 독립성에 비례하는 최소 구현 계획을 세운다. 이미 승인된 계획을 다시
   장황하게 만들지 않는다. 여러 작업으로 나뉘어 계획 문서가 필요하면
   `../plan-authoring.md`로 쓰고, 실행은 `../task-loop.md`로 한 작업씩 닫는다.
6. 제품 코드의 동작을 바꾸는 모든 변경 — 새 기능, 버그 수정, 리팩터링, 동작 변경 — 은
   크기와 처리 방식에 관계없이 실패하는 테스트를 먼저 쓴다. 테스트보다 먼저 쓴 제품 코드는
   참고용으로 남기지 않고 지운 뒤 테스트부터 다시 시작한다. 예외는 버리는 시험 코드, 생성된
   코드, 설정 파일뿐이며 에이전트가 아니라 사용자가 정한다. 문서·문구만 바꾸는 변경은 제품
   코드가 아니므로 대상이 아니다. 테스트 프레임워크가 없으면 가장 작은 재현 스크립트로 같은
   순서를 지키고, 프레임워크 도입 여부는 사용자에게 묻는다.
   | 핑계 | 실제 |
   | --- | --- |
   | 너무 간단해서 테스트가 필요 없다 | 간단한 코드도 깨진다. 테스트는 짧다 |
   | 나중에 테스트를 쓰겠다 | 나중에 쓴 테스트는 바로 통과해 아무것도 증명하지 못한다 |
   | 이미 직접 실행해 봤다 | 직접 실행은 기록도 재실행도 안 되는 일회성 확인이다 |
   | 먼저 짠 코드를 참고로만 두겠다 | 결국 그 코드에 테스트를 맞추게 된다. 지운다 |
   | 기존 코드에 테스트가 없다 | 바꾸는 부분의 테스트부터 추가한다 |
   테스트를 먼저 쓸 때의 규칙:
   - 테스트를 쓰기 전에 어떤 제품 코드 변경이 이 테스트를 실패시킬지 말할 수 있어야 한다.
   - 실행해 실패를 직접 본다. 오류(오타·import)가 아니라 기능이 없어서 예상한 메시지로
     실패해야 한다. 처음부터 통과하는 테스트는 이미 있는 동작을 시험하는 것이다.
   - 통과시킬 최소 코드만 쓴다. 테스트가 요구하지 않는 옵션·확장을 붙이지 않는다.
   - mock의 동작이 아니라 실제 동작을 단언한다. mock은 피할 수 없을 때만, 의존성의
     부수효과를 이해한 뒤에 쓴다. 테스트 전용 코드를 제품 클래스에 넣지 않는다.
   - 회귀 테스트는 빨강-초록으로 증명한다: 수정 상태에서 통과 → 수정을 되돌려 실패 확인 →
     복원해 통과. 한 번 통과한 것만으로 회귀를 막는다고 주장하지 않는다.
   - 통과 확인은 작성한 파일만이 아니라 프로젝트의 전체 테스트 명령이다. 작업 범위는
     산출물의 경계이지 검증의 경계가 아니다. 그 실행에서 보인 실패는 내가 만든 것이
     아니어도 이름으로 보고한다.
7. 코드 전에 `../../security_immune_system/boundary-policy.md`의 risk signal을 분류한다. 신호가 있으면
   `pre-code-security-acceptance`를 수용 조건으로 먼저 남기고 해당 reusable method를 적용한다.
   scanner·release gate를 주장하면 프로젝트가 `project-execution-gate-required`의 실제 command,
   결과, fixture, nonzero failure path를 제공할 때만 그렇게 주장한다.
8. JSON·YAML·skill frontmatter·registry·fixture처럼 선언을 바꾸면 `python3 tooling/verify-semantic-assurance.py`로
   실제 엄격 해석을 먼저 확인한다. 초호기 기관·reusable method·tooling·설치/검증 adapter를 새로 만들거나 바꾸면,
   `../functional_assurance/registry.json`에서 기능 claim·실행 경로·resource·verifier·fixture·산출물·한계를 갱신하고
   `python3 tooling/verify-functional-assurance.py`를 실행한다. 이 검증 없이 해당 자산이
   실제 기능을 제공하거나 release를 막는다고 주장하지 않는다.
9. 필요한 기술·도메인 reusable method와 도구만 선택한다. 방법 선택은 `../method-selection.md`를
   따르되, 프로젝트 leaf는 해당 프로젝트에 실제 코드·CI·fixture가 필요한 반복 적응일 때만 만든다. route는 수용 조건·회귀 위험·검증 증거만 강제한다. 병렬 위임은 경계가
   독립적일 때만 한다.
10. 사용자 제공 스크린샷 또는 명시적 데스크톱·모바일 동작이 있으면, 코드 전에 각
   사용자 가시 변경을 `경로·컴포넌트·데스크톱 상태·모바일 상태·확인 방법`으로 묶은
   간결한 수용 매핑을 만든다. 주석 처리된 영역과 실제 렌더링 상태를 구분하고, 같은
   사용자 문구가 여러 컴포넌트에 있는지 확인한다. 매핑의 각 항목은 실제 경로와
   해당 viewport에서 확인한다. 브라우저나 데이터 조건을 충족하지 못하면 확인하지 못한
   항목으로 보고하며, 모바일에서 단순히 숨겨진 요소를 수용으로 간주하지 않는다.
   반응형 레이아웃은 단일 요소의 폭만 조정하지 말고, 섹션 순서와 인접한 반복 요소의
   열 수·폭·간격·정렬을 같은 breakpoint에서 함께 수용한다.
   PC·태블릿 분류는 기존 고정 데스크톱 폭을 보존하려고 비표준 대형 breakpoint로
   미루지 않는다. 프로젝트의 명시 기준이 없으면 모바일 `0~767px`, 태블릿
   `768~1023px`, PC `1024px~`를 검토 시작점으로 삼고, 각 전환점에서 실제
   컨테이너 폭·열 구성·가로 넘침을 함께 확인한다. 다른 기준을 채택하면 그 이유와
   검증 viewport를 수용 매핑에 남긴다.
   배너·썸네일처럼 고정 비율의 반복 시각 자산은 한 열일 때 남는 컨테이너 폭만큼
   무한히 확대하지 않는다. 자산의 최대폭과 정렬을 먼저 정하고, 여백이 과도해져
   복수 자산이 그 최대폭을 유지한 채 들어갈 수 있을 때 열 수를 늘린다.
   viewport breakpoint는 페이지의 구조 전환에만 쓰고, 재사용 컴포넌트의 열 수는
   실제 컨테이너 폭 또는 intrinsic grid로 결정한다. 중간 폭에서 고정 래퍼 폭이
   급격히 바뀌어 컴포넌트 열 수가 우연히 점프하지 않는지 확인한다.
   반응형 전환 수치를 보고할 때는 `컨테이너 임계값 공식`, `검증한 경로와 실제
   컨테이너 폭`, `viewport 환산에 포함되는 여백·스크롤바·safe area`를 분리해
   기록한다. 임계값의 바로 전·정확한 값·바로 다음 값을 같은 브라우저 환경에서
   확인하고, 환경별 viewport 관측값을 CSS 임계값이나 다른 환경의 보편 수치로
   바꾸어 말하지 않는다.
11. 변경 후 참조 그래프의 직접 소비자와 인접 계약을 검증한다. 사용자 가시 요구는 실제 브라우저와
   해당 viewport에서 확인한다. 자동화 daemon이 sandbox 경계에서 실패하면
   허가된 실행 경계로 한 번 재시도해 실제 측정·스크린샷을 얻고, 그래도 불가능할 때만
   미검증으로 보고한다. 계산된 CSS 값만으로 실제 화면 검증을 대체하지 않는다.
   테스트·린트·타입 검사·빌드·실행 중
   실패한 항목은 출력이 불충분해도 완료로 선언하지 않는다. 가능한 가장 작은 재현·상세 로그·실패
   계층을 확인해 원인 상태와 다음 진단을 남긴다. 사용자 또는 다른 프로세스가 실행 중인
   개발 서버와 같은 출력 디렉터리(예: Next의 `.next`)를 쓰는 production build·clean은
   병행하지 않는다. 격리된 worktree·출력 경계가 없으면 사용자에게 서버 중지·재시작을
   맡기고, 활성 dev 서버의 정상성을 build 성공으로 대체하지 않는다. 범위 밖 설정을 임의로 바꾸지 않으며, 차단이
   해소되지 않으면 미검증 항목으로 종료한다.
12. 실제 실행한 검증, 결과, 남은 위험을 사실대로 보고한다. execution record 계약이 proof를 선언했으면 그 contract에 대해서만 `finalize`로 누락 evidence를 확인한다. 임시 테스트·스크린샷·서버·패치
    산출물은 최종 변경에 남길지와 보관 이유를 확인하고, 전달용 patch는 최종 diff에서 다시 만들고
    깨끗한 기준에 적용 가능한지 검증한다.

<!-- chohogi:section=completion-claim -->
## 완료 주장 관문

완료·수정됨·통과·동작함에 해당하는 말(그 뜻을 함의하는 표현과 만족의 표현 포함)을
하거나, 커밋·PR·다음 작업으로 넘어가기 전에 다음을 순서대로 한다.

1. 이 주장을 증명하는 명령이 무엇인지 정한다.
2. 그 명령을 이번 턴에 전체로 새로 실행한다. 앞선 실행·"통과할 것"은 증거가 아니다.
3. 출력 전체와 종료 코드를 읽고 실패 수를 센다.
4. 출력이 주장을 뒷받침하면 증거와 함께 주장하고, 아니면 실제 상태를 증거와 함께 말한다.

| 주장 | 필요한 증거 | 충분하지 않은 것 |
| --- | --- | --- |
| 테스트 통과 | 전체 테스트 출력: 실패 0 | 이전 실행, 일부 파일만 실행 |
| 빌드 성공 | 빌드 명령 종료 코드 0 | 린트 통과 |
| 버그 수정됨 | 원래 증상 재현이 이제 통과 | 코드를 바꿨다는 사실 |
| 위임 작업 완료 | 변경 diff와 검증 출력 직접 확인 | 역할의 "성공" 보고 |
| 요구 충족 | 요구를 한 줄씩 대조한 목록 | 테스트 통과 |

"~일 것이다", "아마", "~로 보인다"가 나오면 아직 실행하지 않은 것이다.

## 검토 결과 수용

독립 reviewer·사용자·외부 검토자의 지적을 받으면 반응하기 전에 끝까지 읽고, 요구를 자기
말로 다시 서술하고, 이 코드베이스의 실제와 대조한 뒤에 구현한다.

- 여러 항목 중 하나라도 불명확하면 아무것도 구현하기 전에 그 항목부터 묻는다. 항목들은
  서로 얽혀 있을 수 있다.
- 사용자의 지적은 이해한 뒤 구현한다. 외부 검토자의 지적은 이 코드베이스에서 기술적으로
  맞는지, 기존 기능을 깨지 않는지, 현재 구현의 이유가 있는지, 검토자가 전체 문맥을 아는지
  확인한 뒤 구현한다. 사용자의 이전 결정과 충돌하면 먼저 사용자와 논의한다.
- "제대로 구현하라"는 제안은 실제 사용처를 검색한 뒤 판단한다. 쓰이지 않으면 추가가 아니라
  제거를 제안한다.
- 틀렸다고 판단하면 기술적 근거·동작하는 테스트·코드로 반박한다. 확인할 수 없으면 무엇이
  없어서 확인할 수 없는지 말한다.
- 구현 순서: 차단(깨짐·보안) → 단순 수정 → 복잡한 수정. 하나씩 고치고 하나씩 검증한다.
- 맞는 지적에는 동의·감사 표현 대신 무엇을 어디서 고쳤는지만 말한다. 반박이 틀렸으면
  확인한 사실과 함께 짧게 정정하고 진행한다.
- 수용하지 않거나 미룬 지적은 `feedback` 또는 `decision` 이벤트로 이유를 남긴다.

<!-- chohogi:section=integration-closure -->
## 통합 종료

구현과 검증이 끝나 변경을 통합할 차례면:

1. 통합할 바로 그 트리에서 전체 테스트를 다시 실행한다. 실패하면 실패를 보여 주고 멈춘다.
2. 격리 작업공간인지(`git rev-parse --git-dir`와 `--git-common-dir` 비교, submodule이면
   일반 저장소로 취급), 이름 있는 브랜치인지 detached HEAD인지 확인한다.
3. 이 작업이 갈라져 나온 기준 브랜치를 확인한다. 계획·대화·upstream으로 확정되지 않으면
   추정을 말하고 확인받는다 — 잘못된 기준으로의 병합은 되돌리기 비싸다.
4. 통합 방식은 사용자의 결정이다(`authority-lattice.md`의 `external-side-effect`).
   로컬 병합 / push 후 PR / 그대로 보존 중에서 고르게 하고, detached HEAD면 병합을 빼고
   새 브랜치 push 후 PR / 보존만 제시한다. 사용자가 명시적으로 요청하지 않는 한 작업 폐기를
   선택지로 내놓지 않는다.
5. 로컬 병합은 병합 결과에서 테스트를 다시 통과한 뒤에만 작업공간과 브랜치를 정리한다.
   PR과 보존은 작업공간을 남긴다(PR 피드백은 거기서 고친다).
6. 이 작업이 만든 격리 작업공간만 정리한다. 제거가 커밋되지 않은 파일 때문에 거부되면
   `--force`로 밀지 않고 그 파일 목록을 보여 주며 커밋·이동·삭제를 묻는다. push가
   거부되면 원격이 움직인 것이므로 조사하고, force push는 사용자의 명시적 요청이 있을 때만.
7. 폐기는 사용자가 명시적으로 요청했을 때만, 삭제될 브랜치·커밋·경로를 보여 주고 확인을
   받은 뒤에 한다.

## 선택적 능력

- 변경이 여러 독립 파일 경계로 나뉠 때만 병렬 조사·구현을 사용한다.
- 고위험 계약·보안·결제·개인정보 변경에서만 독립 검토를 요청한다.
- React 비동기 상태, 접근성, 성능, 보안 등 구체적 기술 경계가 맞을 때만 해당 reusable method를
  사용한다.

<!-- chohogi:section=exit -->
## 산출물과 종료 조건

산출물은 변경한 것, 수용 조건별 검증 증거, 실행하지 못한 검증, 남은 위험이다.
요구된 변경과 비례한 검증이 끝났거나, 외부 권한·사용자 결정 없이는 더 진행할 수
없는 지점이 명확해졌을 때 종료한다.
